单表数据过亿后，索引失效、写入变慢是迟早的事。分库分表是最终解，但过程要稳。

## 什么时候该分

| 信号 | 阈值参考 |
|------|---------|
| 单表数据量 | > 2000 万行 |
| 写入 QPS | > 5000 |
| 单库磁盘/IO | 持续 80% 以上 |

> [!WARNING]
> 分库分表会永久增加系统复杂度，50 万行以内的表优先考虑归档 + 冷热分离。

## 分片键怎么选

```sql
-- 按用户维度分片（最常见）
shard_id = user_id % 64

-- 全局 ID：雪花算法
SELECT snowflake_id();  -- 时间戳 + 机器号 + 自增
```

选分片键的三个原则：

1. 业务主查询必须能带分片键
2. 分片键要均匀分布（避免按省份这种热点键）
3. 路由方式简单可扩展（取模 → 一致性哈希 → 双层映射）

## 平滑迁移三步走

### 第一步：双写 + 影子表

```java
// 新库双写，旧库照常读
void write(Order o) {
    oldDb.save(o);          // 老路径
    shardRouter.save(o);    // 新路径，失败只记日志
}
```

### 第二步：历史数据回放

```bash
# 按时间窗口分批迁移，每日增量核对
for day in $(seq 1 180); do
  datax --job migrate_orders --where "created_at >= '2025-11-$day'"
done
```

### 第三步：切读验证后整体切换

- 先切读，观察 QPS、慢查询、告警 24 小时
- 再切写，保留 30 天回滚窗口

## 分片后的坑

- 跨分片 `ORDER BY` / 聚合需要 Merge 层
- 非分片键查询要走索引表（`user_id ↔ order_id` 映射）
- 尽量只分表不分库，跨库 JOIN 是噩梦

---

> 分库分表不是银弹，是复杂度换容量，动手前先把索引和归档做到位。
